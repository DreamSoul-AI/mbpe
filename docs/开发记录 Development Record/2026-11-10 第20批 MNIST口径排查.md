# 2026-11-10 第20批 MNIST 口径排查

本批只查 MNIST 上大约 18% 和论文图 6 的 54.23% 差在哪。没有用 GPU，没有下生成模型或量化模型，没有改官方代码。

## 论文原文怎么写这一格

核对的是 arXiv:2411.10281 的 PDF 文本层，以及同一篇的网页排版。PDF 里已经有附录 A 到 H。没有另找一份补充材料把这一格改成别的算法。网页排版把被换行拆开的词拼回去了，下面句子按拼好的词摘录。PDF 里同一段的数字和词序一致：MNIST、Greyscale、256、54.23% 在同一列。

图 6 那一格是：

| 数据集 | 压缩前的表示 | 额外 token | 压缩率 |
| --- | --- | --- | --- |
| MNIST | Greyscale | 256 | 54.23% |

同一张图里，CIFAR-10 在额外 token 为 0 时写的是 100%。说明 100% 就是还没变短。

正文原句：

> We refer to the number of additional tokens in our codebook (vocabulary size increase, not sequence length increase) that our MDBPE produces as extra tokens, and refer to the impact on the sequence length as compression: A compression of 50% describes reducing the sequence length by half, always measured on the unseen testset.

大意：额外 token 是词表里新加的个数，不是序列变长。压缩率看的是序列长度。50% 就是长度变成一半。一律在没见过的测试集上量。

另一处原句把 92% 直接说成序列还剩的比例：

> this reduces compression effectiveness from 50% to 92% of the sequence length

写出序列的原句：

> When writing out the final sequence, we process from top to bottom, left to right, and only write out the token class once per unique ID, at the anchor position. Initially, the token class is e.g. the greyscale value or the VQ-VAE codebook index.

每个 token 只写一次类别，写在锚点上。开头的类别可以就是灰度值。

表 2 的 MNIST 一行写的是 28×28 的灰度，不是缩小或加噪之后的图。附录 C 里“每个通道除以 26”是拿来和别人比彩色图的，不是 MNIST。附录 F 只写了 VQ-VAE 和 VQGAN 的格子大小，没有给 MNIST 再定一档灰度。全文没有把压缩率写成比特，也没有把词表或规则表的存储算进这个百分数。

所以按论文自己的话，这一格是：测试集上，每张图剩余 token 的平均长度，除以 784。额外 token 是 256。灰度就是 0 到 255，不先二值化，也不先降色。单张平均和“总长度除以总像素”在这里是同一个数，因为每张原图都是 784。

## 各口径算出来是多少

用的是已经学好的规则，不再改官方代码。C++ 规则的全量测试集平均长度是 139.364，笔记本规则是 145.225。脚本是 `src/elsner_mnist_metrics.py`。另外用 CPU 重学了两种预处理，每种都是训练集每类 50 张、再套到全部测试集，两次合计约 3 分钟，没有超过 90 分钟。

| 口径 | 结果 | 离 54.23 的距离 |
| --- | --- | --- |
| 剩余长度 / 784（论文定义） | C++ 17.78%，笔记本 18.52% | 大约 36 个百分点 |
| 总长度 / 总像素 | 同上 | 同上 |
| 删掉的比例，也就是 100% 减剩余 | 82.22%，81.48% | 大约 28 个百分点 |
| 每个 token 算成 class、x、y 三个数 | 53.33%，55.57% | 0.90 和 1.34 个百分点 |
| 长度乘以 log2(512)，再除以 784×8 比特 | 20.00%，20.84% | 大约 34 个百分点 |
| 把 512 个词表符号平摊到每张图 | 17.78%，18.53% | 大约 36 个百分点 |
| 每张图再加 256 条规则的 4 个整数 | 148%，149% | 更远 |
| 再加开始符和结束符 | 18.03%，18.78% | 大约 36 个百分点 |
| 灰度先整除 26，再按论文定义重学 | 平均长度 86.75，11.07% | 更远 |
| 大于 0 就记成 1，再重学 | 平均长度 39.51，5.04% | 更远 |

数字在 `results/2026-11-10-elsner-mnist-metrics/summary.json`。

三个整数那一档离 54.23 最近，但不是论文写的口径。论文写明每个 token 只输出一次类别。C++ 虽然在文件里顺手写下 x 和 y，个数仍然按 token 计，不是按整数个数计。53.33% 和 55.57% 也都不是 54.23%。这一档不能拿来宣称对上了。

降色和二值化让重复更多，序列更短，离 54.23 更远。所以差距不是“他们先把灰度压粗了”。

## 结论

论文图 6 的定义和我们第 17、19 批用的定义是同一种：测试集剩余长度除以 784。按这个定义，MNIST 是 17.8% 到 18.5%，不是 54.23%。换比特、词表开销、规则表、开始符、二值化或整除 26，都对不上 54.23%。

差的不是口径看错了。在论文写明的算法和设定下，背景里的 0 会先被大量合并，长度会掉到大约五分之一。论文报出的 54.23% 比这个长得多，正文和附录又没有写出另一种长度公式或另一种预处理。

## 下一步

不要再换公式。下一小步如果还查这个数，只查一种正文没写、但可能让序列变长的做法：合并时跳过灰度 0。那不是论文写的规则，所以本批没有把它当成正确答案去重跑。在这格对上之前，继续不做生成模型，也不做 Zhang。

研究计划里，生成训练、FID、flow matching、自回归和 Zhang 的量化编码已标成暂不做，原文还在。
