# 2026-11-10 第21批 MNIST 差距收尾

本批是 MNIST 压缩率排查的最后一批。没有用 GPU，没有改官方代码。结论先写在这里：MNIST 暂未对上。

## 跳过灰度 0

论文没有写要跳过背景。本批仍按上一批留下的一种可能试了：合并时如果配对里还有原来的灰度 0，这对就不数、也不并。笔画上新编出来的符号不受这条限制。规则仍在训练集每类 50 张上学习，长度在全部 10000 张测试图上量。

测试图里 80.72% 的像素本来就是 0。这些像素一直各自算一个 token。256 个新符号用完后，平均长度占原长 94.84%。比论文的 54.23% 更远，也比不跳过时的 17.78% 更远。

另外看了不跳过、但把“纯背景 token”从长度里拿掉的数。那样只剩带笔画的 token，占原长 14.47%，比 17.78% 更短。背景单独拿出去，对不上 54.23%。

## 1 到 256 个新符号的曲线

用同一套规则，每加一个新符号就在测试集上量一次。图在 `results/2026-11-10-elsner-mnist-gap/curve.png`。

不跳过背景时，长度只降不升。加 1 个新符号是 61.09%，加 2 个是 43.05%，加满 256 个是 17.78%。54.23% 落在第 1 个和第 2 个之间，没有任何一个整数档等于它。离它最近的是只加 1 个新符号，还差 6.86 个百分点。论文写的是 256 个，不是 1 个。

所以不是“他们其实只用了更少的新符号”就能对上。训练图的张数也解释不了最终那个数：以前每类 1 张和每类 50 张，在 256 个新符号下都是大约 18.5%。第一条规则在两种张数下都会是左右相邻的两个 0。

跳过灰度 0 的曲线从高处慢慢降到 94.84%，全程离 54.23% 更远。最近的一点就是用满 256 个新符号的那一点。

## 仓库和论文里还有没有别的线索

README 只说 MNIST 演示可以照着跑，超过 12 像素建议用 C++，并建议先用几百个文件把流程跑通。没有写出 54.23，也没有写训练用了多少张图。

`main.cc` 的注释写明：token 最大编号 255 就是 0 到 255，例子是不用 VQ-VAE 的 MNIST。它把要新加的符号个数写成 32、图写成 12×12，那是示例，不是图 6。

计数是所有图加在一张表里，不是每张图各学一套规则。代码里“每张图”只表示同一对不要在一张图里数两次。

GitHub 上这个仓库只有一条 issue，问笔记本是不是完整版，没有人回复，里面没有压缩率。arXiv 只有 2024-11-15 的 v1，没有另附补充材料。

## 已经排除的

- 论文定义：测试集剩余长度除以 784。我们是 17.78%（C++）和 18.52%（笔记本）。
- 按比特、加上词表或规则表、加上开始符和结束符。
- 把每个 token 拆成三个整数。最近，但是 53.33% 或 55.57%，而且论文写明每个 token 只写一次类别。
- 先二值化，或灰度整除 26。结果更短。
- 合并时跳过灰度 0，或量长度时不算纯背景 token。
- 把新符号个数从 1 改到 256 的任一档。没有一档是 54.23%。
- 训练图用每类 1 张还是每类 50 张。256 个新符号下都是大约 18%。

## 结论

MNIST 暂未对上。

最可能的原因：图 6 的 54.23% 不是用现在公开的代码、按正文算法、在原始 28×28 灰度 MNIST 上量出来的剩余长度。公开的算法会先把成片的 0 并掉，测试集因此掉到大约 18%。论文正文又把压缩率定义成剩余长度除以原来的长度，并写明是 256 个额外 token。两边对不上，仓库和 issue 里也没有第三种说法。

下一步按论文写明的口径去做 CIFAR-10：先有量化格子，再量测试集剩余长度除以该格子的原长。生成模型和 Zhang 仍不做。
