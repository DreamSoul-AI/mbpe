# 2026-11-10 第19批 MNIST 压缩率对照

本批只查 Elsner 论文里 MNIST 的压缩率为什么对不上。没有用 GPU，没有训练，没有做 Zhang 那篇，也没有下载任何东西。官方代码和 `legacy/` 都没改。

## 论文怎么说

正文把压缩率定义成序列还剩原来的多少。压缩率 50% 就是长度变成一半。这个数要在没见过的测试集上量。图 6 的 MNIST 一格是灰度、额外 256 个 token、54.23%。54.23% 乘 784 大约是 425 个 token。

额外 token 指词表里新加的符号个数，不是序列变长。锚点按论文是一个 token 最上面那一行里最左边的像素。邻居只看右边和下面，斜方向不用。每一轮只把出现最多的那一种相邻搭配换成一个新符号，然后继续，直到词表达到预定大小。写序列时从上到下、从左到右，每个 token 只在锚点写一次。位置不另算进长度。

附录里的训练细节讲的是后面的生成模型，不改变上面这套分词。

## 和两份官方代码并排

| 问题 | 论文 | Python 笔记本 | C++ `tokenizer.cc` |
| --- | --- | --- | --- |
| 相邻对怎么数 | 同一张图里，同一对 token 只数一次，哪怕边界上挨着很多个像素 | 同一对锚点只数一次。只看下、右两个方向，所以反方向不会再数到 | 同一对锚点的两个方向都跳过。方向同样只有右和下 |
| 有没有按位置再限制 | 没有。每个像素都可以当起点 | 没有 | 没有 |
| 跳过背景或 0 | 没说要跳过 | 不跳过。0 和 0 挨着照样数 | 不跳过。本批第一条规则就是两个 0 左右相邻 |
| 一轮合并几条 | 只合并出现最多的那一种，所有图上的全部出现都换掉 | 一样，一轮一条规则 | 一样，一轮一条规则 |
| 冲突 | 先扫到的先换。换完之后 class 变了，同一轮里不会再用旧 class 配第二次 | 一个 token 在这一轮里合并过后就跳过 | 从锚点出发，沿偏移跳到另一个锚点才合并。先扫到的先写上新 class，后面的对不上就作罢 |
| 新 token 的形状上限 | 没有。还写明可以是不规整的形状 | 没有 | 没有。形状就是两块拼起来 |
| 词表和停止 | 灰度 0 到 255 是原来的 256 个符号，再加 256 个新符号就停 | `256 + 额外个数`。额外 256 时新符号从 256 编到 511 | 算法相同。但 `main.cc` 写死的是 12×12、只加 32 个新符号，那是示例，不是论文这一行 |
| 长度 | 剩余 token 个数，每个 token 只算一次 | 导出的列表长度，同样不含位置、分隔、填充、结束符 | 写出文件时每个 id 写 class、x、y 三个整数，个数仍是 token 个数，不是三倍 |
| 锚点会不会重算 | 始终是当前形状最上一行的最左像素 | 每次用当前像素重新找 | 合并时选定后就记下来，不每次重算 |

C++ 和论文、笔记本的差别是锚点记法、偏移的正负号、以及合并后用新的 id 还是沿用旧 id。这些都不会把“一轮只合并一种、0 也参与、没有大小上限”改掉。`main.cc` 的 12×12 和 32 个新符号没有拿来当论文设定。

## 按 C++ 重跑的结果

外部脚本是 `src/elsner_cpp_mnist.py`。规则在训练集每类前 50 张、共 500 张上学习，再套到全部 10000 张测试图。灰度用原始 0–255。进程优先级是 Idle，`CUDA_VISIBLE_DEVICES` 为空，线程上限 8。整次大约 124 秒。前两张训练图和前两张测试图都能按 token 形状涂回原来的灰度。

打平时用出现次数最高的那条；次数相同再按符号和偏移的字典序。这次每一轮的最高次数都只有一条，所以打平规则没有影响结果。

| 新符号个数 | 测试集平均长度 | 占原长 |
| --- | --- | --- |
| 1 | 478.96 | 61.09% |
| 2 | 337.48 | 43.05% |
| 8 | 220.10 | 28.07% |
| 32 | 172.82 | 22.04% |
| 256 | 139.36 | 17.78% |

训练这 500 张在 256 条规则后是平均 139.8，占原长 17.83%。

论文的 54.23% 不在这张曲线上。加 1 个新符号是 61.09%，加 2 个已经到 43.05%，中间没有整数档等于 54.23%。加满 256 个是 17.78%。第 17 批用笔记本得到的全量测试集是 18.52%。两份官方算法彼此只差不到 1 个百分点，和论文都差大约 36 个百分点。

第一条规则在 500 张上出现了 291094 次，是左右相邻的两个 0。背景比笔画像素多得多，所以前几条规则就把大片背景并掉，长度掉得很快。再换训练集的张数，也改变不了“先并背景”这件事，因此不会从 18% 拉到 54%。

## 对复现意味着什么

按论文正文写的算法、按笔记本、按 C++ 的计数和替换，在 28×28 灰度和 256 个额外 token 下，MNIST 测试集都压到大约 18%，不是 54.23%。这一行的压缩率还不能算复现出来。差的不是测试集没套上，也不是 Python 和 C++ 谁写错了一行。
