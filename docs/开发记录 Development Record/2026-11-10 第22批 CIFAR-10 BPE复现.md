# 2026-11-10 第22批 CIFAR-10 BPE 复现

MNIST 仍按第 21 批标为暂未对上，本批不再查。CIFAR-10 的图 6 数字本批没有算出来，所以也还没对上。差多少个点说不出来，因为论文量的不是原始 RGB。

## 论文里的 CIFAR-10 设定

图 6 里 CIFAR-10 那一行，压缩前的表示写的是 VQ-VAE，不是灰度，也不是直接的 RGB。额外 token 和压缩率是：

| 额外 token | 压缩率 |
| --- | --- |
| 0 | 100% |
| 256 | 92.38% |
| 512 | 89.16% |
| 1024 | 84.97% |
| 2048 | 79.77% |

0 个额外 token 是 100%，所以这些百分数仍是序列还剩原来的多少。正文原句：

> A compression of 50% describes reducing the sequence length by half, always measured on the unseen testset.

另一处把 CIFAR-10、256 个额外 token 直接写成序列长度的百分比：

> on CIFAR-10, this reduces compression effectiveness from 50% to 92% of the sequence length ... measured for 256 extra tokens

和表上的 92.38% 是同一件事。50% 那一档是不用码本正则时更狠的压缩，92% 是用了正则的 VQ-VAE。图 6 的 92.38% 对的是后一种。

附录 F 原句：

> We apply a VQ-VAE with ... 16^{2}, K=512 for CIFAR-10 at 32^{2} pixels

图片是 32×32。送进 BPE 的格子是 16×16 的码本编号，码本大小 512。原长是 16×16 = 256，不是 32×32，也不是 32×32×3。RGB 不直接当 token。附录 C 写明，CIFAR-10 用的是 VQ-VAE，不是把颜色除以 26 的降色。

规则在多少张图上学会，正文没有写。量长度的集合按上面那句，是没见过的测试集。附录 A 有一个计时例子：5 万张 16×16、再加 128 个新 token。张数和 CIFAR-10 训练集一样，格子也和附录 F 一样，但论文没有把这句话写成“CIFAR 的规则就是这样学的”。

表 2 的 CIFAR-10 一行是生成分数，额外 token 是 1024。那一行的压缩率不在表 2 里，在图 6，对应 84.97%。

## 数据和官方代码

下载前 D 盘大约还有 643 GB。CIFAR-10 官方包约 170 MB，远低于 200 GB，下完也不会让 D 盘低于 100 GB。已下到仓库 `data/`：训练集 50000 张，测试集 10000 张，每张 32×32 RGB。解压后目录和压缩包合计约 340 MB。`git check-ignore` 确认它们落在 `.gitignore` 的 `/data/` 下，不会进 git。

官方 C++ 读的是已经写好的整数格子：文件里先是宽、高，然后每个位置一个整数。`main.cc` 注释写这是导出的 token，例如 VQ-VAE 的编号。仓库里没有 CIFAR-10 的 VQ-VAE 权重，笔记本也只把 VQ-VAE 留成以后替换的注释。本批不允许下载量化模型，所以没有 16×16 的码本编号。

因此没有把原始 RGB 送进切词。那样原长和论文的 256 不一样，算出来的百分比不能和图 6 相减。也没有做 CIFAR 图片的无损还原，因为没有切出 token。

## 结论

CIFAR-10 的图 6 还没对上。不是算出来差了多少，而是论文要的输入这次没有。可能原因就是这一条：92.38% 量在 16×16、码本 512 的 VQ-VAE 格子上，公开的切词程序只接收这种整数格子，不负责把 RGB 变成这些编号。

下一步：先得到和附录 F 一致的量化格子，再按测试集剩余长度除以 256 来量。在那之前不要用原始像素的长度代替图 6。生成模型和 Zhang 仍不做。
