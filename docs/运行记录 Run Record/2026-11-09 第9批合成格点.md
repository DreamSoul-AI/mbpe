长度的基线是同一配置、未训练分词器对同一格点的 token 数。三张格点的基线分别是 4、8、16，合计 28，与格子数相同。压缩比沿用 `CompressionMetrics`：原始 bit 按元素数乘 8，每个 token 按词表大小的对数取整。它不包含词表正文和位置的传输成本，只作报告，不参与门槛。

原始结果在 `results/2026-11-09-synthetic-v1-seeds012/summary.json`。每个种子另有一份版本 1 词表 JSON。

## 结果

三个种子的合计数字相同。每张格点都从基线收成 1 个 token，词表都是 267（初始 256 再加 11 个符号），其中新合并都是 4 步。

| 种子 | 无损还原 | 基线 token | 训练后 token | 变化 | 压缩比 | 词表大小 | 是否过门槛 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 0 | 是 | 28 | 3 | −25 | 8.296 | 267 | 是 |
| 1 | 是 | 28 | 3 | −25 | 8.296 | 267 | 是 |
| 2 | 是 | 28 | 3 | −25 | 8.296 | 267 | 是 |
| 均值 | 是 | 28 | 3 | −25 | 8.296 | 267 | 是 |

单张格点的压缩比也三个种子相同：4 格为 3.556，8 格为 7.111，16 格为 14.222。种子均值 8.296 是这三张的平均，不是把三张拼成一条序列再算。

门槛是序列长度下降并且逐格无损还原。三个种子和均值都过了。

## 结论

在这份版本 1 清单和默认频率阈值下，训练后的序列更短，解码能还原整数格点。压缩比约 8.3，但不能当成压缩率：词表从 256 增到 267，正文成本没有计入，而且每张格点只剩 1 个 token，这个 token 本身保存了整张格点。

种子确实改变了格点取值，三份词表的符号内容并不相同。长度、压缩比和合并步数却完全一样。合并记录下来的是新码字编号之间的配对，编号按出现顺序分配，所以结构相同的合并在三个种子上看起来是同一步。当前规模测不到种子差异，也不能据此比较停止规则、覆盖形状或空间项。

## 观察到的问题

- 默认阈值相对这些小格点太低，每张图都会收到 1 个 token。长度指标在这里饱和。
- 三个种子的报告数字相同，均值没有提供额外信息。
- 压缩比随格子数上升，只是因为 token 数停在 1、词表大小不变。它不反映种子，也不含词表传输。
- 没有下游分数，也没有 FID。

## 建议的下一步

1. 推荐：介观，把清单形状加大，或把频率阈值调到默认配置不再把每张格点收成 1 个 token。理由是长度饱和之后，种子、均值和已有的微观对照都无法在这份设定上分出差别。先让长度还能变化，再谈选边。
2. 微观：在不过饱和的格点上重做已经记录的三项对照，即未知最大对是停止还是跳过、unshuffle 序列还是两格星座、以及已发表的一组空间系数。仍不改 `merge_pair` 的选对。
3. 介观：报告长度或代价时加上词表正文的大小。否则 1 个 token 会显示成很高的压缩比，而还原依赖那个变大的词表。
