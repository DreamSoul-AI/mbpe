# 2026-11-09 第12批第一次分叉

符号上限固定 280，只在版本 2 的 32×32 平铺格点上比较纯次数和已发表空间项。宏观一节没有改。`merge_pair` 没有改。

## 实验设定

| 项 | 取值 |
| --- | --- |
| 命令 | `python -m mbpe controls --diagnose --seeds 0 1 2 --output results/2026-11-09-tile-fork-cap280` |
| 格点 | 清单版本 2 的 `tile`。`--diagnose` 不写时，`controls` 仍是原来的三项对照 |
| 上限 | 280。相对初始 256 个符号，还能新加 24 个。达到后不再开始下一轮 |
| 空间项 | α = 0.3，σ = 2.0，与第 11 批相同，没有搜索 |
| 硬件 | `CUDA_VISIBLE_DEVICES=-1`。与第 9 批同一台机器，Python 3.13.9，torch 2.11.0+cu130 |
| 耗时 | 1.541 秒。没有超过 20 分钟，没有缩小规模 |
| 测试 | `python tests/run.py` 26 项通过，1.872 秒 |

分叉时的 token 数是选出这一对之前还剩下的块数。两边的这个数相同，说明在此之前走的是同一些合并。最终长度与第 11 批上限 280 的次数、空间项一致。完整的嵌套符号在 `summary.json`。

## 结果

| 种子 | 分叉步 | 分叉时 token 数 | 次数选中的对 | 空间项选中的对 | 次数最终长度 | 空间项最终长度 | 无损 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 0 | 9 | 384 | 一串已经合并过的符号，再接原始值 6 | 同一串符号自己配自己 | 172 | 134 | 是 |
| 1 | 1 | 896 | 水平合并过的 (3, 15)，再接 0 | 原始值 14，接水平合并过的 (3, 15) | 197 | 150 | 是 |
| 2 | 8 | 505 | 原始值 8，接一串已经合并过的符号 | 原始值 (2, 2) | 296 | 215 | 是 |

三个种子都无损还原。空间项的最终长度仍都短于纯次数。分叉步不是同一个事件：种子 1 在第二步就分开，种子 0 和 2 先共同合并了 9 步和 8 步。因此不对分叉步取均值。

## 观察到的问题

- 分叉发生得有早有晚。种子 1 的差别来自第二步；另外两个种子要等符号已经嵌得很深。
- 种子 2 的空间项选的是原始对 (2, 2)，次数选的却是一个深层符号。空间项并不总是在“两个原始格子”上改选。
- 一对的正文嵌套很深，单看 JSON 很难读回格子。方向仍写在符号里：`[0, 1]` 是水平，`[1, 0]` 是垂直。
- 最终长度能分开，但第一次分叉的步数不能当成稳定的种子差异。

## 建议的下一步

1. 推荐：微观，仍固定上限 280，只把分叉那一步的两个候选写成“是否还是原始值、方向是水平还是垂直”。理由是长度差距已经知道，现在缺的是这次分叉到底改了方向还是改了嵌套深度。种子 2 的 (2, 2) 和种子 0 的自配不是同一种差别。仍不扫描 α、σ，也不改 `merge_pair`。
2. 微观：先不要把空间项写进现有循环。三个种子的分叉步是 1、8、9，不是一个稳定的改选位置。
3. 介观：诊断输出加一行短摘要，叶子值和方向单独列出。完整嵌套留在 JSON 里，避免下次还要展开十几层才能读。
